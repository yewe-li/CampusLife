# CampusLife 面试讲解与实验路线

这份材料帮助把代码、设计理由和验证证据讲清楚。表达中区分“已实现”“实际验证过”和“下一步想做”；没有亲自完成或理解的内容，不应直接当作个人成果复述。

## 一分钟介绍

CampusLife 是一个校园优惠 Java 后端练习项目，并提供原生 HTML/CSS/JavaScript 演示页面。学生可以按校区、类别和预算找店，用预设账号模拟登录，领取数量有限的免费券，并在“我的券”确认记录；商户只能管理自己的店铺并核销本店有效券。

项目使用 Java 21、Spring Boot、MyBatis、MySQL 和 Redis，控制在五张业务表。重点是三个问题：查询结果和分页总数是否一致，操作人有没有权限，以及多人争抢库存时数据规则能否成立。公开详情使用 Cache Aside，领券依赖数据库条件扣减、唯一约束和同一事务。

前端已支持筛选、详情、模拟码登录、领取、我的券与商户编辑。目前没有真实短信、支付、评价、完整运营后台和云部署。数据是虚构的，业务正确性验证与生产性能是不同证据。

## 按业务链路演示

先按 [运行指南](setup.md) 配置并启动 MySQL/Redis，在 VS Code 打开项目根目录，选择 `CampusLife (dev)` 后按 F5，浏览器访问 `http://localhost:8080`；演示结束按 Shift+F5。launch.json 的 envFile 自动加载已被 Git 忽略的 `.env`，无需在演示中打开或展示凭据。

1. 在页面选择东校区、预算 18 元，对应 API 的 1800 分；解释金额使用分，1800 的等值边界包含，减少一分钱会排除相应店铺。
2. 查询店铺详情和可领优惠，用普通账号申请模拟验证码并登录，展示 token 只代表服务器保存的身份。
3. 领取一次券，再次领取查看重复响应；到“我的券”确认记录，不只看一次成功提示。
4. 换另一用户验证私有记录隔离；换另一商户，在公开详情点击“管理这家店铺”，展示管理详情 GET 返回 403、编辑表单不显示。
5. 正确商户从“商户工作台”打开自有店铺，读取 version 后更新，展示版本递增与旧版本 409；下线后公开详情返回 404，但自有店铺列表仍可查看并重新上线。
6. 用本店商户在工作台的“模拟到店核销”表单核销一张有效券，重复提交得到 409；回到用户账号查询核销状态与时间。使用一次后不会恢复为未核销，不为演示删除已有记录。
7. 展示与这些规则对应的 SQL、测试和执行报告，解释现有缓存一致性窗口。

使用已经运行的 demo 数据时，库存和 version 可能与初始种子不同。应读取当前值再操作，不把重启应用当作重置数据库。

讲解时可以打开 [验证记录](verification.md) 展示对应代码版本和执行日期的证据，并说明单元测试、真实 HTTP 检查与浏览器交互覆盖的区别。旧报告不作为新增功能通过的证据。

## 值得讲清楚的实现

### 为什么数据库是最后一道一人一券防线？

先查领取记录再插入有竞态：两个请求可能同时查到没有记录。`UNIQUE(user_id,voucher_id)` 让数据库在并发时仍只能接受一条。提前查重用于正常情况下的友好响应，不能替代约束。

定位代码：`voucher/VoucherMapper.java` 与 `db/migration/V1__business_schema.sql`。可以进一步解释订单主键、核销码也存在唯一性，不能把所有唯一键异常都叫作“用户重复领取”。

### 为什么条件扣库存还需要事务？

`UPDATE voucher_stock SET stock=stock-1 WHERE voucher_id=? AND stock>0` 解决原子扣减和库存不负的问题。扣完后仍要插入领取记录；若插入失败，必须把扣减一起回滚，否则会出现库存少了但无人取得权益。

事务边界在 `VoucherClaimTransaction`，通过独立 Bean 的代理调用生效。外层 `VoucherService` 在回滚完成后识别重复领取，不在事务内吞掉插入异常。不要用“加了 synchronized”或“先检查库存大于零”解释本项目的并发保证。

### 为什么领取用 READ_COMMITTED，列表用 REPEATABLE_READ？

列表的 items 与 total 要在同次请求看见同一数据视图，因此使用只读 REPEATABLE_READ，并保持筛选一致。

领券采用 READ_COMMITTED：请求在扣库存上等待后，如果另一请求刚好领取成功，后续查重能看到其已提交记录，避免把同一用户的重复请求一律报成售罄。库存安全来自条件更新、约束与事务，不能把“隔离级别较高”直接等同于所有业务更正确。

还要说明边界：稳定排序不冻结不同 HTTP 请求之间的数据；Offset 翻页遇到数据变化或深页时仍有代价。

### 如何防止“已登录就能修改任意店铺”？

身份、角色、归属分别检查。Controller 先验证 token；Service 检查角色为 MERCHANT，再核对数据库 merchant_id；UPDATE 同时带归属与 version 条件。PATCH 只允许规定字段，客户端不能提交 merchantId 改归属。

“我的券”的 user_id 来自服务端认证结果，没有给客户端一个“想查谁就填谁”的入口。并发覆盖由 version 控制：两个相同版本更新最多一个成功，其余返回 409 并要求刷新。

### 一个验证码如何只能被使用一次？

如果按“GET 对比，再 DEL”两个命令处理，并发请求都可能先读到正确值。本项目将对比、错误计数和成功删除放进 Redis Lua，形成原子消费。默认 120 秒有效、5 次错误后销毁；错误尝试不延长有效期。

这个实现只是模拟验证码流程。开发响应直接回显六位码，没有短信投递、真实风控或用户注册。不能把演示模式说成生产手机号登录方案。

### 为什么 token 不是 JWT？

当前需求只需要创建、验证、固定期限到期和退出一套会话。安全随机 token 对应 Redis 中的身份，退出删除会话即可。Redis key 保存 token 摘要，原始 token 返回给调用者；读取不会自动续期。

取舍是受保护请求依赖 Redis，且会话中的角色为登录时快照。若将来支持角色调整、批量踢下线或更多部署拓扑，需要重新设计，不是换一个 token 名称就能解决。

### 为什么修改后删缓存，而且要等提交？

公开详情修改少、重复读多，Cache Aside 便于理解。数据库提交成功后删旧缓存，下次读再回源；如果数据库回滚，就不应提前操作缓存。删除失败不能把已提交更新伪装成“未成功”。

当前正常 TTL 300–330 秒、空缓存 30 秒，Redis 故障可回源，JSON 损坏也回源。必须主动说明旧读可能在删除后重新填旧值，TTL 提供恢复机会，但没有任意时刻强一致或精确刷新延迟承诺。TTL 抖动不等于已经解决热点击穿。

### 为什么 Redis 故障有两种处理？

公开详情的正确来源仍在 MySQL，所以缓存不可用可以降级。登录身份依赖 Redis 会话，故障时无法确认操作人，必须返回认证服务不可用。不能为了“提高可用性”把受保护操作直接放行。

### 五张业务表有什么必要？

用户表表示身份；店铺表表示经营归属和展示信息；券表表示优惠规则；库存表表示剩余名额；领取记录表表示个人权益。拆库存有助于隔离频繁修改的数字，但不会自动制造高吞吐能力。

领取记录保存当时的 useEnd 作为 expiresAt；店铺下线后历史记录仍能查到。当前 shopName/voucherTitle 查询的是关联表现值，不是完整的历史名称快照。新增核销流程使用期限快照、店铺归属与记录状态判定，成功时写入核销时间和商户身份；它不等于消费订单和满减结算。

### 为什么同一张券核销只能发生一次？

Service 在一个事务内按唯一核销码 `SELECT ... FOR UPDATE`，再检查归属、状态和领取期限；拿到锁后才读取当前时间，防止等待跨过期限却继续通过。条件更新再次限定 `ISSUED`、未过期和归属，一次写入状态、核销人和时间。第一个请求提交后，后续请求看到已核销，返回 409，而不是再次成功。

这是领取记录的行锁，不是 Redis 分布式锁。库存只在领取时扣减，核销不再扣；下线店铺与关闭活动不撤销已发券，期限以领取记录的 expiresAt 为准。要说明这只是商户确认使用，不包含消费额校验与付款。

### 有联合索引就算优化完成了吗？

不能。要看查询条件是否符合索引前缀、范围条件之后还能用哪些部分、是否需要额外排序，以及真实数据的选择性。店铺联合索引围绕 status、campus、category、average_price、id，省略中间条件时效果可能不同。

讲优化之前应保留 EXPLAIN、数据量、请求分布与前后耗时测量。没有这些证据，就准确说“为常见筛选建立了索引”，不说“性能提升数倍”。

## 用证据回答追问

| 需要证明的规则 | 合适的证据 |
| --- | --- |
| 参数和权限分支正确 | HTTP 状态、业务错误码、数据库未被错误修改 |
| 一人一券 | 同用户并发请求、唯一记录数、库存仅减少一份 |
| 没有超发 | 多用户争有限库存，核对成功记录数、剩余库存和非负约束 |
| 插入失败会回滚库存 | 真实数据库注入插入失败后，比较库存与记录，再验证可重试 |
| 更新后缓存失效 | 先回填 Redis，更新成功后检查 key，再读新值；另测删除故障不虚报更新失败 |
| 缓存降级、认证拒绝放行 | Redis 异常路径分别检查公开读与受保护操作 |
| 仅本店商户、有效券只核销一次 | 权限拒绝、期限等值边界、同一核销码并发后仅一次状态变更，核销字段和库存核对 |
| 数据持久存在 | 有明确操作步骤和重启后的查询结果，不能只引用一次进程内单测 |

执行入口与报告目录见 README。浏览器测试命令为 `npm run test:e2e`，依赖配置见 [运行指南](setup.md)；它操作真实页面，仍需结合执行日期和具体断言解释覆盖范围。并发正确性测试中的线程数、请求数只是测试场景，不是 QPS、峰值容量或生产用户量。覆盖率也不是正确性的完整证明。简历若填写数量、覆盖率或压测结果，应附可复现命令、环境、时间和原始报告。

集成测试会重置数据，因此保护检查在 Flyway 之前运行，只接受数据库 `campuslife_test`、Redis DB 1 与精确测试前缀，并拒绝绕过校验的替代连接配置。可以解释为什么“执行 reset.sql 前检查库名”还不够：Flyway 若先启动，错误连接已经可能产生写入。

运行环境也有明确限制：Flyway 11.7.2 对 MySQL 8.4 提示超出其已测试范围，本机迁移与集成测试通过不等于官方认证；开发库已经执行 V900，不能仅切换 prod profile 就继续复用。开发演示、测试隔离与生产初始化是不同问题。

## 可以独立完成的后续实验

这些内容属于练习建议，未作为现有能力交付：

- 给查询加入一个真正的业务条件，确保列表与 count 一起修改，并解释索引可能受什么影响。
- 验证 UTC 开始时刻、结束时刻和微秒精度边界，不依赖电脑本地时区碰巧一致。
- 复现缓存删除后旧请求回填，先画出并发顺序，再选择是否需要版本门禁或事件驱动失效。
- 用相同数据集比较 Offset 与游标分页，记录限制，不只比较一次耗时。
- 独立说明核销行锁和乐观版本锁的区别，再添加一个期限边界变式测试；不要仅复述现有测试名字。

> 实现校园优惠后端练习项目，基于 Spring Boot、MyBatis、MySQL 与 Redis，覆盖条件筛选、商户归属校验、限量领券与个人权益查询，并提供原生页面串联演示流程；使用条件扣库存、唯一约束和数据库事务维护领取规则，通过版本控制处理商户并发修改，并实现公开详情缓存及 Redis 故障降级。

测试结果单独补充经验证的证据，不添加虚构访问量、线上用户量或吞吐提升。明确这是带演示前端的本地教学项目，真实短信、支付和完整运营后台未实现。可结合 [简历表述](resume.md) 与 [验证记录](verification.md) 按自己的实际贡献调整。
