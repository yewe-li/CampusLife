# CampusLife 简历与演示材料

适用：Java 后端实习／校招。以下是依据参考工程组织的表述模板，不是对个人独立能力的认证。项目在 AI 协助下实现；使用前应能讲解并现场修改相关代码，按实际贡献选择条目，角色与完成时间如实填写。

## 简历可用版本

**CampusLife 校园优惠平台｜Java 后端学习项目**

技术栈：Java 21、Spring Boot、MyBatis、MySQL、Redis、JUnit 5、Flyway。

- 实现校园店铺条件筛选、模拟验证码登录、商户自有店铺管理、限量领券、个人领取记录查询及一次性核销，采用五张业务表、统一响应与请求编号，并提供可直接演示的页面和 OpenAPI 文档。
- 通过 InnoDB 条件扣库存、用户与优惠券联合唯一约束、同一事务内写入领取记录保证领取规则；在真实 MySQL/Redis 测试中，64 用户以 32 并发争抢 20 张券恰好成功 20 次，同用户 32 并发仅产生 1 条记录，并验证插入失败时库存完整回滚。
- 实现 Redis 公开详情缓存、空值缓存、TTL 随机偏移及事务提交后失效；使用版本号处理商户并发修改，区分缓存故障回源与身份服务故障拒绝操作，通过真实 HTTP 集成测试覆盖权限、缓存与事务场景；具体数量和执行版本以验证报告为准。

若版面很紧，可保留后两条和一行项目介绍。不要把这个项目描述为已经上线运营的商业平台，也不要把自动生成的代码当作自己已掌握的知识。

## 五分钟现场演示

1. VS Code 打开项目根目录，确认 MySQL/Redis 已启动，按 F5；访问 `http://127.0.0.1:8080/`。
2. 选择东校区、咖啡、预算 18 元，展示真实筛选与详情。解释接口以“分”存储金额。
3. 用页面中的种子账号获取**模拟验证码**登录，领取并查询我的券；重复领取应提示已领取。本机验收曾使用 `13800000001` 领取券 1，可换第二个学生账号展示首次领取。
4. 切换对应商户，修改自家店铺信息；说明后端会拒绝其他商户与普通用户，旧 version 返回 409。从“商户工作台”的自有店铺列表说明下线后仍可管理与重新上线；在“模拟到店核销”表单按需演示核销与重复核销冲突。
5. 打开 `VoucherIT` 与 [验证报告](verification.md)，讲清条件更新、唯一约束、事务回滚各自负责什么。

仓库提供可选 Playwright 浏览器测试入口；页面验证范围见对应执行记录。正式面试演示前，自己在浏览器完整走一遍上述步骤；接口验证不自动等于页面点击验收。

## 必须能回答的追问

- 为什么“先查是否领过”不能单独防并发？哪条数据库约束负责最终判断？
- 为什么将领券事务放在独立 Spring Bean？异常在哪里被映射，库存在哪里回滚？
- 为什么采用 READ_COMMITTED？等待最后一份库存后再次查重复记录有何作用？
- 事务提交后删缓存是否等于强一致？旧请求回填和删除失败会产生什么窗口？
- 为什么 Redis 故障时店铺详情可回源，而我的券不能绕过会话检查？
- 乐观锁的 WHERE version 条件失败时，为什么返回 409 而非静默覆盖？
- 一次 64 用户的正确性测试能证明什么，不能证明什么？
- 核销行锁与修改店铺的版本锁分别解决什么问题？为什么拿到行锁之后才读取当前时间？

讲解可参考 [架构与一致性](architecture.md) 和 [面试讲解](interview.md)。当前没有真实短信、支付、微服务、消息队列或生产监控告警平台，不将这些技术列为已实现。业务思路参考原始文档注明的课程场景，说明自己的学习来源与实际改动。
